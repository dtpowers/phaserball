# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Earkandi Pinball — a statically-hostable 2D pinball game themed around the [earkandi](https://earkandi.net/) brand, built with Phaser 3 and Vite. Fully implemented and playable.

## Commands

```bash
npm run dev       # Start Vite dev server (localhost:5173)
npm run build     # Production build to dist/
npm run preview   # Preview production build locally
npm run gen-sfx       # Generate audio SFX files (scripts/gen-sfx.js)
npm run clean-sprites # Remove white fringe from bumper PNGs (scripts/clean-sprites.js)
```

## Architecture

**Vite config** ([vite.config.js](vite.config.js)): `root: '.'`, `publicDir: 'public'`, build outputs to `dist/assets`. ES module project (`"type": "module"` in package.json). Dependencies: `phaser@^3.80.1`, `planck@^1.5.0` (physics). DevDependencies: `vite@^5.4.0`, `sharp@^0.34.5` (image processing), `@playwright/test@^1.60.0` (browser testing).

**Four Phaser scenes:**
- **BootScene** — Loads 5 audio SFX (bumper-hit, ball-drain, flipper-activate, kick, hihat) + 5 custom bumper PNG sprites (4 round + 1 triangular slingshot `bumper-angle`) + flipper PNG sprite, then procedurally generates remaining visual assets (ball, 3 UI buttons) via Phaser Graphics + `generateTexture()`. Launches MusicScene, then starts GameScene.
- **MusicScene** — Persistent background scene launched once from BootScene, never stopped. Owns `BPM = 110` and `BEAT_MS = 60000 / BPM` (~545ms) as the single source of truth for all beat-synced features. Runs a looping `time.addEvent` that plays the `kick` audio sample each beat and broadcasts `this.game.events.emit('beat', { interval: BEAT_MS })` so any scene can subscribe. Double-start guard: `if (this._beatEvent) return` in `create()` prevents duplicate timers if the scene is somehow re-entered.
- **GameScene** — Main gameplay: table walls, bumpers, flippers, ball physics, scoring, lives, input, launch power bar. Subscribes to `game.events.on('beat', this._onBeat, this)` in `create()` and unsubscribes in `shutdown()`. `_onBeat({ interval })` stops the previous glow tween (tracked as `this._glowTween`) then creates a new one: all `_bumperGlows` circles flash from alpha 0.35 → 0 over `interval` ms (`Sine.easeIn`), syncing the glow to the kick drum. **Important:** The old `killTweensOf(array)` pattern was a no-op — Phaser checks individual targets, not the array object. Track the tween reference and call `.stop()` directly.
- **GameOverScene** — Overlay (launched via `scene.launch()`, then GameScene is stopped). Receives `{ score, highScore }` via `create(data)`. Shows final score, high score, a pulsing tween on the high score *value* text when `score >= highScore`, restart button that stops GameOverScene then calls `scene.start('GameScene')`.

**Game config** ([src/main.js](src/main.js)): Resolution 700×1050 (portrait), `Phaser.Scale.FIT` with `CENTER_BOTH`, `physics: false` (physics handled by Planck.js standalone world), 3 active pointers for multi-touch, `disableContextMenu: true` for mobile. Exposes `window.phaserGame = game` after construction so DOM scripts can access the Phaser sound manager.

**Entry point:** `index.html` mounts Phaser into `#game-container` (wrapped in `#game-wrapper` flex column for responsive layout), imports `src/main.js` as module. CSS prevents scroll/zoom on mobile. Uses **Fredoka One** Google Font for HUD labels.

**HTML overlay for HUD:** Score, lives, and high score rendered as HTML elements in `#game-header` (layout: HI SCORE left, SCORE center, LIVES right). Labels ("SCORE:", "HI SCORE:") use `.hud-label` class for animated rainbow color cycle. Element IDs updated from scenes via `document.getElementById()` — NOT drawn in Phaser:
- `#score-value` — current score number; JS toggles `.score-pop` class on increase to trigger shake animation
- `#hi-value` — high score number; updated on game start and on new high score
- `#lives-display` — lives icons; set via `'⚪'.repeat(lives)`

**Mute button:** `<button id="mute-btn">` inside `#game-container`, absolutely positioned `bottom: 12px; right: 12px` (requires `position: relative` on `#game-container`). Shows 🔊/🔇. Toggling calls `window.phaserGame.sound.setMute(bool)` to mute/unmute all Phaser audio globally. State persisted in localStorage key `earkandi_muted` (`'true'`/`'false'`). Applied on every page load — the inline `<script type="module">` runs after `src/main.js` (document order), so `window.phaserGame` is guaranteed set. Both localStorage calls are wrapped in `try/catch` for Safari private mode safety.

Responsive via `clamp()` font sizes.

### Physics (Planck.js)

Physics uses Planck.js (Box2D JavaScript port) via a standalone world, NOT Phaser's built-in Matter.js. Import: `import * as planck from 'planck';` ([GameScene.js:2](src/scenes/GameScene.js#L2)). Phaser config has `physics: false`.

**Scale conversion:** `SCALE = 100` (100 px = 1 m), with `toM(px)` / `toPx(m)` helpers. Box2D requires meter-scale (~0.1–10 m) for solver stability. All physics constants are defined in **MKS units** (meters, m/s, kg/m³). Visual sprites are created in pixel space and synced from body positions each frame via `toPx()`.

**World:** `this._world = new planck.World({ gravity: { x: 0, y: GRAVITY_Y } })` (Y-down to match Phaser), stepped each frame in `update()`: `world.step(1/60, 10, 8)`. In `create()`, the world **must** be instantiated before `buildTable()` since `buildTable()` calls `_world.createBody()`. `GRAVITY_Y = 5` (NOT 9.8): a real pinball playfield is tilted only ~6.5°, so the ball's down-table acceleration is `g·sin(6.5°) ≈ 1.1 m/s²`; full vertical gravity makes the ball plummet (feels heavy *and* fast). 5 is a middle ground — weighty/controllable but lively. It's a single constant used in all three places gravity is (re)set (world creation, end of `buildFlippers()`, and `releaseCharge()`).

- **Walls** — Static `planck.Box` bodies, restitution 0.3, friction 0.4. All positions/sizes in meters. Includes left/right/top borders, bottom plates (gap for drain), launch lane divider, launch lane bottom stop, two funnel guides (angled via `Phaser.Math.Angle.Between()`), and corner deflector (45°). Wall visuals drawn as 8px stroke outlines via Graphics in pixel space. **Funnel fixtures use `filterCategoryBits: 0x0002`** so that flipper bodies (which use `filterMaskBits: 0xFFFD`) never generate contacts with them — without this filtering, the flipper body at rest overlaps the funnel geometry and the contact constraint fights the RevoluteJoint, causing a spasm. The ball uses default mask `0xFFFF` and still bounces off funnels normally.
- **Bumpers** — Static `planck.Circle` bodies (r=0.36 m), restitution **1.0** (elastic — lively bounce that does NOT inject energy). It was 1.25, which added 25% speed on every hit and rocketed the ball to the velocity clamp — the main cause of the "too fast" feel. Keep bumper restitution ≤ 1.0. Fixture userData stores `{id, points, type, sprite}` — `id` is a sequential integer starting at **0**, used for collision debouncing. Collision detected via `this._world.on('begin-contact')`, and `_getBumperFixture()` reads userData directly from the contact fixture (no map iteration). **Important:** the null check must use `data.id === undefined || data.id === null`, NOT `!data.id` — falsy check breaks for id=0 (first bumper), silently dropping all hits on it. Visual sprites are custom 250×250 PNG images scaled to 0.288 (~72px), set to **depth 1**. Each bumper has a beat-synced glow circle overlay (stored in `this._bumperGlows[]`, initial alpha 0, driven by `_onBeat` tween) at **depth 0** — drawn above the background (also depth 0, but created earlier) and behind the bumper sprite (depth 1). **Critical depth rule:** never use `setDepth(bumper.depth - 1)` for the glow — `bumper.depth` defaults to 0, so this produces depth -1 which is behind the background and invisible. **Bumper positions are centered on the play area, not the full table.** The play area runs x=16–612 (center x=314); the launch lane occupies x=612–700 and is excluded. When adjusting bumper X positions, always center them on x=314. The current layout was derived by proportional rescaling: `x_new = (x_old − 350) × (596/668) + 314`, where 668px = old inner width (16–684) and 596px = play area width (16–612).
- **Slingshots** — Two triangular **active-kick** bumpers in the lower corners (`angleBump.png` → `bumper-angle`), mirrored across the play-area center (x=314): left at x=90, right at x=538, both y=660 — positioned so each triangle's innermost corner roughly vertically aligns with the outer (away-from-center) edge of the flipper below it. Static `planck.Polygon` (3-vertex triangle) with `restitution: 1.0`. **The polygon is derived from the sprite's alpha** — three rounded-corner centers sampled from `angleBump.png` (sprite-local px, origin at center: top-left `(-372,-287)`, right `(393,177)`, bottom `(-222,337)`), inset ~6% toward the centroid so collision hugs the visible triangle. Constants in `SLING`/`SLING_LOCAL_PX` ([GameScene.js](src/scenes/GameScene.js)). Sprite scaled `0.12` (~100px wide) at **depth 1**, rotated ±90°; the polygon mirrors x (`flip ? -p.x`) to match `setFlipX`, and the body `angle` = sprite rotation so shape and sprite stay locked. **Orientation:** the long flat striking face points toward table center (left/right are full `(rot, flip)` swaps of each other, preserving mirror symmetry). Each carries a beat-synced glow circle (radius 60) in `_bumperGlows` and `userData.kick` (an outward **direction** `{x,y}`, normalized in the handler: left `(1,-1)` = up-right, right `(-1,-1)` = up-left). **Kick:** on hit the generic `begin-contact` handler **redirects** the ball outward along `kick` at exit speed `max(incomingSpeed, SLING.MIN_EXIT) + SLING.BOOST` (8.0 + 3.0 → ~11 m/s, clamped by `MAX_SPEED`); points 200. It *redirects* rather than *adds* a velocity delta because `begin-contact` fires before the bounce resolves — the inbound-into-the-face velocity opposes an additive kick and partly cancels it, which felt weak. Redirecting gives a consistent brisk pop regardless of incoming angle. Slingshots reuse the same scoring/popup/glow path as round bumpers (sequential `userData.id`, ids 9 and 10). The collision handler's sprite-pop tween reads `bumperSprite.scaleX` (NOT the `BUMPER_VIS.SCALE` constant) so the pop scales correctly for both the 0.288 round bumpers and the 0.12 slingshots.
- **Flippers** — Dynamic polygon bodies (8-vertex convex polygon, intentionally inset from the sprite edge) connected to ground via `planck.RevoluteJoint` with motor + angle limits. **Planck.js `Settings.maxPolygonVertices = 12`** — the previous 17-vertex polygon was silently reduced to a broken 8-vertex convex hull, cutting a large triangle out of the bottom-left pivot area. Always keep flipper vertices ≤ 12. **The flipper sprite's silhouette is non-convex** — the large circular hub on the left is the tallest part, but the body narrows immediately to the right. A convex polygon connecting hub-top to near-tip is forced to draw a straight line that overshoots the actual body surface in the mid-flipper region, causing the ball to bounce off thin air above the visible sprite. Fix: inset all vertices clearly inside the sprite rather than tracing the outer edge. Hub top at (-0.55, -0.18) instead of the sprite's actual peak; no intermediate upper-body vertex (it made the phantom zone worse); pivot end pulled in to (-0.74, -0.07) to avoid the funnel wall. Accept that the hub hitbox is slightly smaller than the visual hub — the body surface (where the ball normally rolls) is what matters. Three motor speeds: `FLIPPER_MOTOR_UP = 18` rad/s (snap to active), `FLIPPER_MOTOR_HOLD = 3` rad/s (hold at active angle), `FLIPPER_MOTOR_DOWN = 12` rad/s (return to rest), `FLIPPER_MAX_TORQUE = 200` N·m. **Asymmetric joint limits so rest = a hard limit:** the body is created at the rest angle (jointAngle 0) and the rest motor drives *toward a limit*, so the rest angle MUST coincide with a limit or the flipper drifts away from where it's drawn. Left fires by decreasing jointAngle → limits `[-FLIPPER_ACTIVE_RAD, 0]` (rest = upper); right fires by increasing → `[0, +FLIPPER_ACTIVE_RAD]` (rest = lower). (Previously both used symmetric ±45°, so rest sat 45° from the drawn angle and the flipper visibly jumped to its true equilibrium on first fire — the "right flipper starts beyond the funnel wall until fired" bug.) Rest angle: ±15° (sign flipped per side so both tilt slightly down). **Mirrored geometry**: left flipper body extends RIGHT from pivot; right extends LEFT. Therefore opposite motor directions produce the same visual tip motion — left: negative motor (CCW) = tip up, right: positive motor (CW) = tip up. State machine in `update()`: fire (motor UP) → hold (motor HOLD at active angle via `upDir * angle >= FLIPPER_ACTIVE_RAD`) → return (motor DOWN to rest). Pivot positions in meters (`PIVOT_X_L: 1.216`, `PIVOT_X_R: 5.144`, `PIVOT_Y: 8.35`). The pivot was lowered from 8.20 to 8.35 to prevent the ball from getting wedged between the funnel wall and the flipper outer edge; this also brought the flipper body into slight overlap with the funnel physics body, which is resolved by collision filtering (see Walls entry). Sprite angles synced from `body.getAngle()` each frame. Sprite loaded from `flipper.png` (1224×417) scaled to `156/1224` (~156px wide, ~53px tall). Right flipper uses same texture with `setFlipX(true)`, and its **collision polygon is mirrored** (`verts.map(v => ({x:-v.x, y:v.y})).reverse()` — negate x, reverse to restore CCW winding) so its thin/pivot end matches the flipped sprite instead of putting the wide/tip end at the pivot. Fixture density: `0.1 kg/m³`.
- **Ball** — Dynamic `planck.Circle` body (r=0.16 m), `bullet: true` (continuous collision detection), restitution 0.5, friction 0, density 0.001 kg/m³, `linearDamping: 0.05`, `fixedRotation: true`. Spawn position in meters (`SPAWN_X: 6.52, SPAWN_Y: 9.50`). Visual sprite created separately via `this.add.image()` and synced from body position each frame. Damping is intentionally **light** (gentle playfield rolling friction): higher values (e.g. 0.2) bleed enough of the low-gravity ball's energy that it dead-stops in pockets/slopes (it got wedged between the left funnel guide and the flipper pivot — recoverable with a flip, but it feels dead).
- **Launch lane closure** — Static `planck.Box` body (0.375×0.08 m, angle -15.5°) spawned when ball exits the lane upward (checked in meters: `pos.x < toM(600) && pos.y < LANE.FUNNEL_Y && vel.y < 0`). Has matching Graphics visual (4px line, color `0x3a3a6a`). Removed on ball respawn. **The closure check must be guarded with `this._ballBody` (`if (!this._launchClosureBody && this._ballBody)`):** the drain check earlier in the same `update()` frame can call `loseLife()`, which synchronously nulls `_ballBody`. The relaunch block above it already re-checks `this.ball && this._ballBody`, but the closure block did not — so a drain that occurs while no closure exists (e.g. a ball killed by the slingshot kick or the 2s safety fallback before it ever sealed the lane) dereferenced null and crashed the update loop (frozen game).
- **Velocity clamp** — After each `world.step()`, ball velocity clamped to `BALL.MAX_SPEED` (16 m/s) as a top-speed cap / anti-tunneling safety net. Velocity is already in m/s from Planck, compared directly. Box2D uses standard velocity integration (no Verlet), so `setLinearVelocity()` is safe without positionPrev concerns.
- **Gravity control** — During launch charge: `world.setGravity({ x: 0, y: 0 })` (ball floats). On release: `world.setGravity({ x: 0, y: GRAVITY_Y })` (gravity restored).

**Planck.js Gotchas:**

- **Fixture density should be passed in `createFixture()`.** If you call `fixture.setDensity()` after creation, you must also call `body.resetMassData()` to recalculate mass/inertia — Planck.js does not do this automatically. Without mass, dynamic bodies have `invInertia === 0`, which causes RevoluteJoint motors to be skipped entirely by the solver (Box2D's `fixedRotation` path). Always prefer: `body.createFixture(shape, { density: 0.1 })`.
- **`physics: false` disables all Phaser physics methods on sprites.** With no Phaser physics subsystem, sprites have no `setVelocity()`, `body`, or physics-related properties. All motion must be handled through the Planck world — call `planckBody.setLinearVelocity()` on the physics body, then manually sync the Phaser sprite's position/angle in `update()`.
- **All physics constants use MKS units.** Ball speeds, positions, sizes, flipper dimensions, and table boundaries are all in meters/seconds/kg. Pixel values only appear in visual rendering code (Graphics, sprite positions). When adding new physics behavior, define constants in meters and convert to pixels only for visual sync.
- **Flipper motor directions are opposite per side due to mirrored geometry.** Left flipper body extends RIGHT from pivot; right extends LEFT. In Box2D's Y-down system, positive motor = CW rotation. Because of the mirrored geometry, the SAME CW rotation drives the left tip DOWN but the right tip UP. Therefore: left flipper uses negative motor (CCW) to lift, right uses positive (CW). The state machine tracks `upDir` per side (`left: -1, right: 1`) for motor direction and active angle checks. Never unify both flippers to the same motor direction — they must be opposite.
- **Planck.js `Polygon()` silently computes a convex hull and caps at `Settings.maxPolygonVertices = 12`.** If you pass more than 12 vertices, Planck selects only the extreme hull vertices — the actual shape used is often radically different from what you wrote. Always test the output vertex count with `shape.m_vertices.length`. For the flipper polygon, the old 17-vertex definition was being reduced to 8 vertices, cutting a large triangle out of the pivot-end bottom. Current shape uses 8 vertices intentionally inset from the sprite edge (see Flippers entry for why tracing the outer edge causes phantom collisions).
- **A constant-speed motor drives to a joint LIMIT, not to a target angle.** `RevoluteJoint.setMotorSpeed()` just sets an angular velocity; with `enableLimit`, the body coasts until it hits a limit, where the limit constraint holds it. So a flipper's resting pose is defined by *a limit*, not by where the body was created. If the body's initial/drawn angle (jointAngle 0) isn't itself a limit, the motor will move it to the nearest limit on the first frame (`setMotorSpeed` also wakes the body) and the visual will jump. Make rest coincide with a limit (asymmetric limits per side) — see the Flippers entry above.

### Game mechanics

- **Launch:** Hold Space (or touch launch button) to charge — gravity disabled (`_world.setGravity({x:0, y:0})`), power accumulates (`delta * chargeRate`, frame-rate independent), ball velocity zeroed on Planck body. `startCharge()` guards against `!this._ballBody` to prevent crashes during the 1-second respawn delay (body is null between `loseLife()` and `spawnBall()`). Release fires ball with velocity in m/s: `yVel = -(BASE_VEL_Y + launchPower * VEL_SCALE)`, `xVel = VEL_X` (-0.1 m/s leftward drift), clamped to `BALL.MAX_SPEED`. Gravity restored. Launch constants: `MAX_POWER: 2600`, `CHARGE_RATE: 0.9`, `BASE_VEL_Y: 2.0 m/s`, `VEL_SCALE: 0.0042 m/s per power unit` (full charge ≈ 12.9 m/s — clears the lane and top deflector under `GRAVITY_Y`; a light tap dribbles back for a relaunch), `VEL_X: -0.1 m/s`. These are tuned to `GRAVITY_Y` — re-derive if gravity changes.
- **Relaunch:** If ball falls back into launch lane (`pos.x > LANE.DIVIDER_X (6.20m) && pos.y > LANE.FUNNEL_Y (5.20m) && vel.y > 0`), `ballLaunched` resets to false, allowing another charge-and-launch.
- **Velocity clamp:** Ball speed capped at 16 m/s post-`world.step()` in `update()` (top-speed cap / anti-tunneling).
- **Lives:** 3 lives, `isLosingLife` guard prevents double-drain. Ball drain detected when `pos.y > toM(TABLE.H)`. Safety fallback: if launched ball stays below y=980 (converted via `toM()`) for >2s, force drain. On life lost: screen shake (200ms, 0.03 intensity), Planck body destroyed + Phaser sprite destroyed, ball respawned after 1s delay. Lives display initialized in `index.html` and updated via `document.getElementById()`.
- **Game over & restart:** When lives reach 0, high score saved to localStorage (`earkandi_highscore`), GameOverScene launched as overlay, GameScene **stopped** (not paused). PLAY AGAIN calls `scene.start('GameScene')`, which re-runs the full `init`→`create` lifecycle. **Critical:** Phaser reuses the *same scene instance* across restarts, so instance fields survive a restart. The standalone Planck world is NOT a Phaser-managed object, so its bodies must be dropped on teardown — otherwise `create()` builds a new world and `spawnBall()` calls `newWorld.destroyBody(staleBodyFromOldWorld)`, which throws inside Planck's broad-phase, aborts `create()`, and leaves the scene stuck in `CREATING` (no update loop = frozen — this was the long-standing "Play Again doesn't work" bug). Two layers guard this: (1) `create()` clears `this._ballBody`/`this.ball` up front; (2) a `shutdown()` wired via `this.events.once(Phaser.Scenes.Events.SHUTDOWN, ...)` nulls the Planck world + body refs when the scene stops. **Do NOT** call `super.shutdown()` (Phaser.Scene has no such method) or manually destroy children/tweens in `shutdown()` — Phaser already destroys display objects, tweens, timers, and input on shutdown; doing it yourself races with Phaser's teardown.
- **Scoring:** Star=100, Heart=150, Moon=200, Flower=250, Slingshot=200 (plus an active velocity kick — see Slingshots under Physics). Score popups animate upward and fade on bumper hit. On score increase, JS adds `.score-pop` class to `#score-value`, then removes it on `animationend` to allow re-triggering. The `#score-value` element lives in the DOM (not the scene), so `create()` calls `updateScoreDisplay()` on (re)start to reset it to 0 — otherwise it shows the previous game's score until the first hit.

### Asset pipeline

**Custom bumper sprites:** 4 PNG images (250×250, transparent BG) in `public/assets/images/`: `star.png`, `heart.png`, `moon.png`, `flower.png`, plus the triangular slingshot `angleBump.png` (844×725, transparent BG). Loaded in BootScene `preload()`, referenced as `bumper-star`, `bumper-heart`, `bumper-moon`, `bumper-flower`, `bumper-angle`. Used by bumpers, background decorative shapes, and GameOverScene. Sprites were cleaned of white fringing via `scripts/clean-sprites.js` (alpha erosion 2px + white-background defringe). All five (incl. `angleBump.png`) are listed in the script's `sprites` array. **Erosion is not idempotent** — each run shrinks the alpha by another 2px — so the script is meant to be run once on a fresh export. When adding a single new sprite to an already-cleaned set, run the defringe+erode on just that file (one-off) rather than re-running the whole script over the already-clean ones.

**Flipper sprite:** `flipper.png` (1224×417 PNG, transparent BG, cropped from original 1536×1024) in `public/assets/images/`. Loaded in BootScene `preload()`, scaled to `156/1224` (~156px wide, ~53px tall) in GameScene. Right flipper uses same texture with `setFlipX(true)`.

**Procedural assets (BootScene `generateAssets()`):** Ball (32×32 white circle), 3 UI buttons (left/right arrow + launch up-arrow).

**Audio:** Generated via `scripts/gen-sfx.js` (WAV files in `public/assets/sfx/`): `bumper-hit.wav`, `ball-drain.wav`, `flipper-activate.wav`, `kick.wav` (sine sweep 150→60 Hz, 200ms — kick drum placeholder), `hihat.wav` (white noise burst, 80ms — hi-hat placeholder). All files are drop-replaceable: overwrite any WAV with a custom sample of the same name. `hihat` is played on every bumper collision (replaced the old `bumper-hit` sound). `kick` is played by MusicScene every beat.

### Visual features

Gradient background (dark blue-black top → dark navy bottom) with 15 decorative shapes that float, rotate, and bounce off walls/each other (frame-based physics, not tweens), beat-synced bumper glow (flashes alpha 0.35 on kick, fades to 0 by next beat via `Sine.easeIn` tween), **pulsing amber launch lane** (amber fill rect clamped to the lane interior `fillRect(628, 512, 56, 512)` — x=628–684 between the inner edges of the divider and right walls, y=512–1024 matching the divider wall's span — + bright amber divider stroke at x=620 from y=512 to y=1024, both breathing alpha on 1800ms `Sine.easeInOut` yoyo tween. **Both must stay clamped to the wall span**: the fill originally ran the full table height (x=612–700, y=0–1050) and the stroke ran to `TABLE.H`, bleeding above the wall top, below the bottom stop, and under the right wall), **flowing launch-lane chevrons** (a column of 5 amber `^` carets via Graphics, centered at the lane center x=656, from y=580 to y=960; each runs an alpha pulse tween 0.15→0.9 yoyo `repeat:-1` with a per-caret start `delay` that *decreases* toward the top — `(CHEV_COUNT - 1 - i) * 180` so the bottom caret peaks first — making the bright spot sweep upward in a continuous loop to signal "launch up"; stored in `this._laneChevrons`, Phaser auto-disposes on shutdown), launch power bar (green→red gradient, only visible while charging; fill scale formula: `(launchPower / MAX_POWER) * 20` to match the 200px background height), score popups on bumper hit, screen shake on life lost, rainbow-animated HUD labels, score pop effect on score increase.

**Phaser API Gotchas:**
- **`fillGradientStyle` signature is `(topLeft, topRight, bottomLeft, bottomRight, alphaTopLeft, alphaTopRight, alphaBottomLeft, alphaBottomRight)`.** Alpha values default to 1 if omitted. Passing extra positional arguments (e.g., width/height) silently maps onto the alpha slots and makes the fill invisible. Always pass exactly 4 colors + up to 4 explicit alpha values.

## Phaser Skill

A Phaser-specific development skill is installed at `.claude/phaser-game-development-1/SKILL.md`. Key principles: scene-first architecture, composition over inheritance, physics-aware design, asset pipeline discipline, frame-rate independence. See the skill for anti-patterns to avoid.
